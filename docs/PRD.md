# 易闻查词 · 产品需求文档（PRD）

> 目标：从当前的前端 Demo，演进为可与 **零克查词**、**句易网** 正面对标的小红书违禁词检测产品。
> 本文档是工程与运营的执行依据，按优先级组织，带验收指标。

- 文档版本：v1.0
- 状态：草案 / 待评审
- 适用分支：`claude/zen-clarke-gveu8u`

---

## 0. 一句话定位

> **小红书赛道最不会漏、且唯一能告诉你「为什么标红、出自哪、你的赛道能不能用、怎么改」的违禁词工作台。**

横向工具（零克/句易）给你一本字典；易闻给你一个发布前的合规决策闭环。

## 1. 现状盘点（v0 Demo）

### 1.1 已具备（资产）
- 完整的产品叙事与 UI：检测工作台、出处详情卡、AI 改写对比、发布预览、历史复盘、我的词库、会员、词库后台。
- 四级风险体系：`ban / high / warn / qual`（禁用 / 高危 / 提醒 / 需资质可用），其中 **`qual`（需资质可用）是横向工具表达不了的差异点**。
- 词条结构已包含差异化字段：`why / law / clause / trackNote / example / fix[]`。
- 赛道（垂类）框架：通用 / 美妆 / 医疗 / 母婴 / 食品 / 穿搭。

### 1.2 致命缺口（决定生死）
| 缺口 | 现状 | 风险 |
|---|---|---|
| **词库规模** | 21 主词 / 88 变体（`app/data.jsx`） | 对手数万条，差三个数量级，无竞争力 |
| **检测召回率** | `text.indexOf()` 精确匹配（`app/engine.jsx`） | 任何对抗写法（夹字/谐音/拆字/拼音/全半角）全漏，漏检=卸载 |
| **词库更新机制** | 词库写死在 `.jsx` 静态常量 | 无法更新；而"替你盯规则"正是付费理由 |
| **后端 / 账号 / 数据** | 纯前端 localStorage | 无法做团队、批量、API、数据沉淀、跨端 |
| **准确率验证** | 无评测集 | 改词库无法回归，质量不可控 |
| **AI 改写** | 取 `fix[0]` 静态字符串替换 | 不是真改写，无语义与语气适配 |

### 1.3 结论
- **守住**：垂直定位 + 解释力 + 改写闭环（这是赢点）。
- **补齐**：召回率追平句易网（这是入场券）。
- 战略不是"抄成句易网"，而是 **召回率追平 + 解释/改写远超**。

## 2. 目标用户与场景

| 用户 | 核心诉求 | 付费意愿 |
|---|---|---|
| 个人博主 / 素人 | 发布前自查，别被限流 | 中（低客单） |
| 美妆 / 母婴 / 医疗类博主 | 赛道资质判定（特证能不能宣称） | 高 |
| 品牌方 / 商家 | 笔记批量合规、报备前过审 | 高 |
| MCN / 代运营 | 团队批量检测、API 接入、统一词库 | 最高（B 端） |

**核心场景**：博主写完笔记 → 粘贴/选赛道 → 检测标红 → 看每处的原因与出处 → 一键或逐条改写 → 发布预览确认 → 存入复盘。

## 3. 北极星指标与质量基线

- **北极星指标**：周活跃检测笔记数（WAU × 人均检测篇数）。
- **质量基线（v1 必须达到，否则不上线）**：
  - 召回率（漏检率）：核心违禁词集 **召回 ≥ 98%**。
  - 误报率：**≤ 5%**（误报伤体验但不致命，召回优先）。
  - 检测延迟：单篇（≤2000 字）服务端 **P95 ≤ 300ms**。
  - 词库规模：上线起步 **≥ 3000 主词**，半年 **≥ 10000**。
  - 词库更新：**每周** 至少一次公示更新。

## 4. 功能需求（按优先级）

### P0 — 内核（没有这步，一切免谈）

#### 4.1 抗对抗检测引擎（重写 `engine.jsx` → 服务端）
对抗写法是小红书违禁词的常态，必须识别：
- **归一化预处理**：去零宽字符、去空格/标点夹字、全角↔半角、繁↔简、大小写、emoji 夹字剔除、形近字归一。
- **拼音 / 谐音**：`zui好`、`威❤️信`、`v➕`、`薇`。
- **拆字 / 同义扩展**：`微 信`、`徽信`、近义词库映射。
- **多模匹配**：AC 自动机（Aho-Corasick）替代逐词 `indexOf`，支撑万级词库下 P95≤300ms。
- **保留原文定位**：归一化后命中要能映射回原文 `start/end` 用于标红（关键工程难点）。
- **分级评分**：保留现有 `LEVEL_WEIGHT` 思路，参数可配置。

**验收**：对 200+ 条对抗样本（夹字/谐音/拆字混合）召回 ≥ 98%。

#### 4.2 词库结构化与规模化
- 词条 schema（见 §6），从 21 条扩到 **3000+**。
- 词库与代码解耦：存数据库，引擎启动时加载、支持热更新。
- 六大类（极限词/医疗功效/特殊宣称/站外导流/虚假诱导/数据造假）各自成规模。

**验收**：词库可通过后台增删改而无需发版；引擎热加载生效。

#### 4.3 后端化
- 检测 API：`POST /api/detect`（入参 text/track/enabledCats，返回 tokens/matches/score）。
- 词库存储：DB（PostgreSQL/MySQL）+ 缓存（Redis/内存 AC 树）。
- 前端 `detect.jsx` 数据源从静态 `LEXICON` 切到 API。

#### 4.4 评测集与回归
- 200–500 条人工标注真实笔记（含正例/负例/对抗例）。
- CI 中跑准确率/召回率，词库或引擎变更触发回归。

---

### P1 — 把好叙事接到真内核

#### 4.5 真·AI 改写
- 替换 `engine.jsx:137` 的 `fix[0]` 静态替换。
- 调用大模型：输入原文 + 命中清单 + 赛道语气要求，输出"去违规 + 保留语义 + 小红书口吻"的改写。
- 保留现有左右对比 UI（`modals.jsx` 的 `RewriteModal`）。
- 合规评分变化可视（改写后重新检测）。

#### 4.6 账号体系与数据持久化
- 登录（手机号/微信）、会员状态、历史、自定义词库迁移到服务端。
- 跨端同步，替换现有 localStorage。

---

### P2 — 更新与信任（付费的真正理由）

#### 4.7 运营后台真实化
- 现 `AdminView` 为只读演示 → 改为真 CRUD：增删改、审核、版本、灰度发布。
- 权限分级（运营/审核/管理员）。

#### 4.8 规则更新日志（续费情绪价值）
- 每周公示新增/调整词条，前台可见"本周更新了 X 条"。

#### 4.9 误报 / 漏报反馈回流
- 用户一键反馈 → 进运营队列 → 反哺词库。**数据飞轮的起点。**

---

### P3 — 对手做不到的护城河

| 功能 | 价值 | 对手能否做 |
|---|---|---|
| **图片/封面 OCR 检测** | 小红书封面图违禁词同样限流，横向工具基本不查 | 难 |
| **批量检测 + 开放 API + 团队空间** | MCN/品牌方付费意愿最强 | 部分 |
| **赛道资质智能判定** | 上传产品备案号→自动判断"美白/防晒"能否宣称，把 `qual` 做成真功能 | 不能 |
| **发布前后效果归因** | 接平台数据，验证"改写后流量更好"，闭环最值钱一环 | 不能 |

## 5. 技术架构

```
┌─────────────┐     ┌──────────────────┐     ┌─────────────────┐
│  前端 (Web)  │────▶│  检测服务 (API)   │────▶│  词库引擎        │
│  React       │     │  /api/detect      │     │  AC自动机 + 归一化 │
│  检测/改写/复盘│◀────│  /api/rewrite(LLM)│◀────│  + 拼音/谐音/拆字  │
└─────────────┘     └──────────────────┘     └────────┬────────┘
                            │                          │
                            ▼                          ▼
                    ┌──────────────┐          ┌─────────────────┐
                    │ 账号/会员/历史 │          │ 词库 DB + 缓存   │
                    │  (DB)         │          │  + 运营后台维护   │
                    └──────────────┘          └─────────────────┘
                                                       ▲
                                              运营增删改/规则更新/误报回流
```

- **前端**：保留现有 React 组件资产，数据源切 API。建议逐步迁出 CDN + Babel 运行时（`index.html`），改为构建产物。
- **检测服务**：Node/Go 均可；引擎核心是内存中的 AC 自动机 + 归一化管线。
- **词库存储**：DB 持久化 + 启动加载到内存 AC 树 + 热更新（版本号/订阅）。
- **AI 改写**：服务端调用大模型，做提示工程（赛道语气、保留语义、合规约束）。

## 6. 词库数据模型（schema）

在现有字段基础上规范化（现状见 `app/data.jsx`）：

```jsonc
{
  "id": "ext_0001",
  "word": "最好",
  "aliases": ["最佳", "最优", "最棒"],   // 显式变体
  "variants_auto": true,                  // 是否启用引擎自动变体(拼音/夹字/拆字)
  "level": "ban",                         // ban|high|warn|qual
  "cat": "extreme",                       // 六大类
  "tracks": ["auto"],                     // 适用赛道; qual类需配资质规则
  "qual_rule": null,                      // 需资质词的放行条件(如"国妆特字")
  "platform": "广告法",
  "law": "《中华人民共和国广告法》第九条",
  "clause": "广告不得使用「最佳」等用语。",
  "why": "属绝对化用语，机审直接判极限词并限流。",
  "trackNote": "全赛道禁用，无资质豁免。",
  "example": "2023年某美妆店铺因「最佳效果」被罚10万元。",
  "fix": ["很喜欢的", "回购多次的"],
  "source_url": "",                       // 出处链接(可追溯)
  "version": "2026-06-25",                // 词条版本
  "status": "active"                      // active|review|deprecated
}
```

新增字段相对 v0 的关键：`qual_rule`（资质判定）、`variants_auto`（引擎自动变体）、`version/status/source_url`（更新与可追溯）。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 词库冷启动慢（规模上不去） | 先聚合公开极限词表打底，再人工精修出处/赛道/案例；误报回流持续补充 |
| 法规/平台规则变化快 | 运营周更机制 + 更新日志；source_url 可追溯 |
| 召回与误报权衡 | 召回优先；误报靠分级（warn 而非 ban）和"需资质可用"软化 |
| 改写质量不稳定 | 提示工程 + 改写后强制复检 + 人工兜底改写模板 |
| 合规免责 | 全程保留"仅供参考、不具法律效力"声明（现 README 已有） |

## 10. 下一步落地建议

按依赖关系，工程第一刀切在 **§4.1 抗对抗检测引擎 + §4.2 词库结构化**——它同时解决"会漏检"（致命）与"词库太小"（无竞争力）两个根本问题，其余功能都依赖它。

建议落地顺序：评测集打底 → 归一化管线 → AC 自动机 → 词库 schema 迁移与扩充 → 后端 API → 前端切源。
